# スコアリングモデル — 頑張りはどう紫陽花になるか

> 「量」と「種類」をどう1輪のネオン紫陽花に変換するかの正本。
> 見え方は `ビジュアルディレクション.md`、使われ方は `画面フロー.md` を参照。

## 1. 大原則：「量」と「種類」を完全に分離する【確定】

ひとつのマスに咲く1輪を、交わらない2軸で決める。

- **量**（その日どれだけ行動ログがあるか）→ 小花序の**数**、毬の**密度・大きさ**
- **種類**（何カテゴリに触ったか）→ 小花序ごとの**色**

紫陽花は小さな花序の集合なので、複数カテゴリの日が「塗り分けた1枚の花」ではなく、
「いろんな頑張りが同じ日に集まって咲いた毬」として自然に読める。

### なぜ分けるか

「種類の数」を豪華さに流すと、広く浅い日が過剰に大きく見えてしまう。
広さは色数、量は花序数/密度に逃がすことで、**多カテゴリの日**と**行動量の多い日**を別の輝き方で両立する。

## 2. 標準花：ネオン紫陽花1系譜【確定】

標準成長は「別の花に変わる」ではなく、**紫陽花の毬が育つ**モデルにする。
コスモス/ダリア等は標準段階ではなく、季節テーマ・月間ハイライト・特別演出の候補に退避する。

| 段階 | 見た目 | 意味 |
|---|---|---|
| 芽（双葉） | 小さな双葉/芽 | ちょっとやった日（床） |
| 小さな紫陽花 | 少数の花序、余白あり | 少なめ |
| 普通の紫陽花 | 手まり状にまとまる | ふつう（充実した一日） |
| 大きな紫陽花 | 密度が上がり、毬が育つ | 頑張った日 |
| 大手まり | 表示上限近くまで花序が詰まる | かなり頑張った日 |

### 紫陽花として効くパラメータ

- **花序の重なり**：整然とした十字ではなく、少しずらして重ねる。ピンウィール感が最重要
- **カテゴリ内の色ゆらぎ**：同一カテゴリ内だけ淡さ/微小な色相ズレを許す。カテゴリ間はソリッドに読ませる
- **ドーム状の塊**：中心を密に、外周を少し小さく外向きにして毬として見せる

小花序の形は未確定。紫陽花らしい4萼ピンウィールと、相談中に好感触だった「浅い切れ込み5枚」パターンを
SwiftUIプロトタイプで比較する。小マスでは葉脈や中心星などの細部は描き込まず、形・色・密度だけで読ませる。

## 3. 量の境目：「点 ＝ 小花序の数」【確定】

**1カテゴリの1点 ＝ 小花序1つ**。行動を 軽=1 / 中=2 / 重=3 で点にし、その点数ぶん各カテゴリ色の小花序が乗る。
合計点＝花序数で、毬のサイズ/密度が決まる。

| 合計点(=花序数) | 表示段階 | 表示方針 |
|---|---|---|
| 1〜2 | 芽（双葉） | 花序ではなく芽で描く |
| 3〜5 | 小さな紫陽花 | 少数の花序を余白ありで配置 |
| 6〜8 | 普通の紫陽花 | 小さな手まりとして成立させる |
| 9〜16 | 大きな紫陽花 | 中心密度を上げて毬を育てる |
| 17〜 | 大手まり | 表示は約24花序で打ち止め |

**根拠**：育児パパの普通の日（仕事2＋家事育児2＋運動2など）を「普通の紫陽花」に着地させる。
9点以上は普通の日では届きにくい位置に置き、かなり動いた日の特別感を残す。

### このモデルの効き目

- **色の配分が自動**：点の比＝花序の比。仕事8割の日は紫の花序が多い
- **各カテゴリ最低1花序が自動**：1点入れば必ず1花序（薄くても証）
- **2軸が独立**：色数が増えても点が増えなければ毬は大きくならない
- **紫陽花の意味と合う**：複数カテゴリの日が「混ざった毬」として自然に見える

### 上限と表示【確定】

- **1カテゴリの点に上限なし**：コードに全振りした日なども内部スコアでは報われる
- **内部の点は青天井でOK**（連続日数・累計・月間ハイライトに使える）
- **表示はおおむね24花序で打ち止め**。小マスで潰れるのを防ぐストッパー。超過分は内部スコアへ

```swift
enum HydrangeaStage {
    case sprout
    case small
    case normal
    case large
    case full
}

func stage(for total: Int) -> HydrangeaStage {
    switch total {
    case ..<3:   return .sprout
    case 3...5:  return .small
    case 6...8:  return .normal
    case 9...16: return .large
    default:     return .full
    }
}

func displayedFloretCount(for total: Int) -> Int {
    min(max(total, 0), 24)
}
```

## 4. 点の付け方：行動ログ → 点【方針確定・中身は未決定】

点は「ユーザーの自己申告による頑張り度」ではなく、**行動ログからの定量/準定量**で決める。
ユーザーに聞くのは「何点？」ではなく、**「今日残しておきたいものはある？」**。

### 入り口を2系統に集約

| 入り口 | 性質 | 点への変換 |
|---|---|---|
| GitHub（コミット/PR） | 数えられる | コミット数・PR・リリース等→関数 |
| HealthKit（運動・睡眠） | 数えられる | 距離・時間・ワークアウト・睡眠時間→関数 |
| X 投稿 | 文章 | FMで行動リスト抽出→カテゴリ/点の仮置き |
| 音声/手動メモ | 文章 | FMで行動リスト抽出→カテゴリ/点の仮置き |

**原則**：数えられるものは関数（FM不要）。文章で来るものだけFMが行動リスト化し、下記の打ち込み量バンドで点を仮置きする。

### 点の強度＝「打ち込み量」で決まる【確定】

軽=1 / 中=2 / 重=3 は**行動ごとの固定ラベルではなく、その日その行動にどれだけ打ち込んだか（時間 or 回数）**で決まる。「10分の作業は1、しっかりやれば2〜3」という直感に合わせ、たくさんやれば点も順次上がる。

- **物差しはカテゴリ相対**：勉強は分単位、仕事は件数単位、と「ふつう」のスケールが違うため一律の分数では測らない（一律10/30/60分だと8時間勤務が即3になり「普通の日=6点」が壊れる）
- **sub-linear（頭打ち＝3）**：記事5本でも3で止める。読書だけで毬が育ちすぎないように。超過分は内部スコアへ（既存の「24花序打ち止め」と同じ思想）
- **成果語フロア**：リリース / PRマージ / 登壇 は時間が短くても最低3（「5分だが超重い」を守る）
- **休息・睡眠は達成フロア型**：「7時間寝た」「休めた」は達成で固定点（睡眠＝中2目安、休めた＝軽1）。寝た時間に比例して花序を増やさない（寝るほど毬が育つ矛盾を防ぐ）。からだカテゴリ内で運動と合算され、暴発は24花序打ち止めで吸収
- **自動入力との二重カウント回避**：GitHub（commit数）・HealthKit（運動・睡眠）が連携で点を出す日は、それを正本にする。同じ行動がX/メモからも来たらFMは同一行動として扱い、加算しない。連携OFF/データ無しの日のみテキスト側がフォールバック

### 行動→点 初版テーブル【確定・実機チューニング前提】

| カテゴリ（色） | 軽=1 | 中=2 | 重=3 | 物差し |
|---|---|---|---|---|
| 学習・開発（ライム） | 〜15分 / 記事1〜2本 / commit1〜2 | 〜45分 / 3〜4本 / 〜5commit | 45分〜 / 5本〜 / リリース・PRマージ・登壇 | 時間 or 回数 |
| からだ（アクア） | 散歩〜15分 / 休めた一日 | 運動〜45分 / 睡眠7h達成 | 運動45分〜・大会 | 時間・達成（HealthKit自動。睡眠は達成フロア型） |
| 趣味・交流（ゴールド） | ちょっと触れた | がっつり楽しんだ | イベント・登壇・コミュニティ参加 | 時間 or 回数 |
| 仕事（バイオレット） | 半休など軽め | 通常勤務（通常の対応件数） | 繁忙・残業・大型案件 | 対応件数 |
| 家事・育児（ピンク） | ちょい手伝い（1タスク） | 通常の家事育児（送り迎え+風呂+寝かしつけ等3タスク前後） | 看病・通院などの重い日 | タスク数 |

**着地確認**：通常勤務(2) + 通常の家事育児(2) + ランニング45分以内(2) = 6点 → 「普通の紫陽花」。育児パパの普通の日が狙いどおりここに乗る。


### ユーザーができること【確定】

- 抽出された行動を削除する
- カテゴリを直す
- 抽出漏れの行動を追加する
- 「残したい」ハイライトを選ぶ

ユーザーは点数を直接いじらない。主観的な「めちゃくちゃ大変だった」は花の量を増やすのではなく、
ハイライト、メモ、星、子どものリアクションなどの**記憶レイヤー**に逃がす。

### フィルタ【確定】

- Xはリプライ・引用を除外、本人の発信のみ（FM以前のフィルタで弾く）
- 1カテゴリの点上限は設けない（表示の暴発は24花序打ち止めで吸収）
- 不明な文章は低めに倒す。強い成果語（リリース、登壇、完了、PRマージ等）があるときだけ重くする

## 5. FoundationModel 前提の割り切り【確定】

自分専用・iPhone最新機・Apple Intelligence有効を前提とし、**汎用配布向けフォールバックを最小化**する。

- FMの担当は**文章から行動候補を抜き出すこと**
- 点の最終感覚をFM任せにしすぎないため、よくある行動は固定値テーブルに寄せる
- FMは未知の文章を「行動候補・カテゴリ・軽中重の仮置き」に変換する

```swift
@Generable
struct ActivityCandidate {
    @Guide(description: "短い行動名") let title: String
    @Guide(description: "カテゴリ") let category: Category
    @Guide(description: "強度。軽=1、中=2、重=3") let intensity: Intensity
    @Guide(description: "抽出理由") let reason: String
}
```

### 最小退避【確定】

- `SystemLanguageModel` が稀に `.unavailable`（DL中・AI機能オフ）→ 入力を「未分類の中=2」で一時記録
- 後でユーザーがカテゴリ修正できるように、元テキストは端末内に残す
- 同じ行動が日替わりで揺れないよう、よくやる行動だけ固定値テーブルを残す

## 7. カテゴリと配色【確定】

種類軸（色）の中身。検討の結果カテゴリを改定：**交流は趣味に吸収**、**からだ（運動・休息・睡眠）を独立カテゴリに追加**（HealthKit自動）。
枠数は5のまま中身が入れ替わった。「からだ」は当初「運動」だったが、休息・睡眠も**身体を整える＝身体ケア**として同じ屋根に入るため上位概念で括った（6色目を作らず5枠を維持）。

配色の前提：背景が紺の夜の庭なので**紺に溶ける色（特に青）は使えない**（「仕事=青」の定番が使えないのはこのため）。
色相をホイール上で約70°間隔に均等配置 → (a)同系色が隣り合わない／(b)加法混色で濁らない、の両方が成立。

### 基本5色

| カテゴリ | 色名 | HEX | メモ |
|---|---|---|---|
| 仕事 | バイオレット | `#A77BFF` | 落ち着いた集中の色 |
| 家事・育児 | ピンク | `#FF5C9E` | 温かさ・家庭。ユジュの花と揃う |
| 学習・開発 | ライムグリーン | `#6FE85C` | GitHubの草。イン/アウト両方ここ |
| からだ | アクア | `#25DDD0` | 運動・休息・睡眠。水・回復・コンディション。HealthKit自動 |
| 趣味・交流 | ゴールド | `#FFC93C` | 遊び・宝物。登壇/コミュニティもここ |

### ライトUI用インク変種【確定】

基本5色は紺の庭で光る前提のネオン値。白背景のUI（図鑑・設定・シェアカード）ではゴールド・ライム・アクアが沈むため、別途インク版を持つ。
**ルール＝色相は固定したまま、白背景でコントラスト3.0:1（WCAG AA図形・アイコン基準）になる明るさまで濃くする**。目標値を1つ決めれば全色が一律に導出される。

| カテゴリ | 庭のネオン（正本） | ライトUIインク | 白 / 紺 コントラスト |
|---|---|---|---|
| 仕事 | `#A77BFF` | `#A77BFF`（元々3.0で変更なし） | 3.0 / 5.2 |
| 家事・育児 | `#FF5C9E` | `#FF549A` | 3.0 / 5.3 |
| 学習・開発 | `#6FE85C` | `#25AC10` | 3.0 / 5.3 |
| からだ | `#25DDD0` | `#12A69C` | 3.0 / 5.2 |
| 趣味・交流 | `#FFC93C` | `#C18B00` | 3.0 / 5.2 |

- 庭画面は常にネオン正本（追従しない）。インクは**UI部分のライトモード時のみ**使う。
- 3.0:1はアイコン・凡例ドット・色付き太字向けの最低ライン。小さい本文に色を載せるなら4.5:1へ上げる余地あり（同ルールで再導出するだけ）。
- ゴールドは濃くするとブロンズ寄りになるが、別コンテキストの機能色として割り切る。

### カスタム用ストック（追加色・4色が上限）

基本5色の色相の隙間（4ヶ所）の中間に置く。70°間隔がすでに埋まっているため5色目は必ずどれかの隣になる。

| 色名 | HEX |
|---|---|
| コーラル | `#FF6A4D` |
| ローズ／マゼンタ | `#E85CD0` |
| スカイブルー | `#4FA8FF` |
| ミント | `#4FE3A8` |

### 注意点（実装時）

- 仕事のバイオレットが紺地に最も近い → 沈むなら一段明るく（`#B891FF`）or 割り当て変更を検討
- 最も近いペアは 学習・開発(緑) ↔ 運動(アクア)（色相67°差）→ 両方やった日に隣り合わせない配置を配色ルールで効かせる
- カテゴリ間はグラデーションで連続させない。凡例性が死ぬため、花序ごとはソリッド色で置く
- カテゴリ内だけ `hueDrift` で淡さ/隣接色相への微小な揺れを許す

### 中心の芯と「白熱」の扱い【確定】

- **中心の白熱（色数が多いほど白く輝く）は廃止**：幅（種類）は花序のカラフルさで十分伝わり二重表現だった
- **中心の芯＝淡いクリーム1色で固定**（`#F5EFD8`〜`#FBF3DD`、色数に関係なく常に同じ）
  - 芯が共通だと色違いの花が並んでも「同じ品種感（1系譜）」が芯からも効く
  - 純白(`#FFFFFF`)は無機質で芯だけ浮くため暖色寄りの淡い白に
- 種類軸はこれで**花序ごとの色**に単純化
